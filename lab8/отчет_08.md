### 2. Логическое резервное копирование

Выполнено логическое резервное копирование с использованием утилит `pg_dump` и `pg_dumpall`. Основные наблюдения:

**Простой дамп и восстановление:**

- Утилита `pg_dump` с форматом custom (`-Fc`) создает компактные сжатые дампы
- Восстановление через `pg_restore` позволяет выборочно восстанавливать объекты
- Все данные и структура таблиц восстановились полностью

**Параллельный дамп:**

- Опция `-j` позволяет использовать несколько потоков для ускорения дампа
- Формат directory (`-Fd`) необходим для параллельного дампа
- `pg_dumpall --globals-only` сохраняет глобальные объекты (роли, табличные пространства)

**Проблемы при загрузке:**

- Несовпадение кодировок может вызвать ошибки при восстановлении
- Важно проверять совместимость параметров исходной и целевой БД

Логическое копирование гибкое и позволяет восстанавливать данные между разными версиями PostgreSQL, но может быть медленным для больших БД.

### 3. Физическое резервное копирование и PITR

Освоено физическое резервное копирование и восстановление на определённый момент времени.

**Базовая резервная копия:**

- `pg_basebackup` создает полную копию кластера на уровне файловой системы
- Формат tar (`-Ft`) со сжатием (`-z`) экономит дисковое пространство
- `tablespace_map` позволяет изменить расположение табличных пространств при восстановлении
- Физическая копия быстрее логической для больших объёмов данных

**PITR (Point-in-Time Recovery):**

- Настройка непрерывной архивации WAL через `archive_command` обеспечивает сохранение всех изменений
- Параметры `wal_level = replica` и `archive_mode = on` активируют архивацию
- Файл `recovery.signal` указывает PostgreSQL выполнить восстановление
- `restore_command` определяет, как получать архивные WAL-файлы
- `recovery_target` позволяет восстановить БД на конкретный момент времени

**Сравнение режимов восстановления:**

- Восстановление без `recovery_target` применяет все доступные WAL-файлы (2000 записей)
- Восстановление с `recovery_target = 'immediate'` останавливается сразу после достижения консистентности (1000 записей)
- PITR критически важен для восстановления после логических ошибок или удаления данных

Физическое копирование быстрее и обеспечивает точное восстановление состояния кластера, но требует больше настройки и дискового пространства для архивов WAL.

### 4. Обновление сервера

Выполнена миграция данных между версиями PostgreSQL с использованием логического метода.

**Процесс обновления:**

1. Создание полного дампа исходной БД с помощью `pg_dump`
2. Создание табличного пространства в новой версии
3. Восстановление дампа в целевую БД с указанием табличного пространства
4. Проверка целостности данных и доступности пользователей

**Ключевые моменты:**

- Логический дамп совместим между мажорными версиями PostgreSQL
- Права доступа пользователей сохраняются в дампе
- После миграции пользователь может работать с данными без дополнительной настройки
- Табличное пространство можно указать при создании БД или изменить позже

## Выводы

**Логическое и физическое копирование:** Освоила оба подхода к резервному копированию. Логическое копирование (`pg_dump`, `pg_dumpall`) гибкое и совместимо между версиями, но медленнее. Физическое копирование (`pg_basebackup`) быстрее и создаёт точную копию кластера, но требует одинаковой версии PostgreSQL и архитектуры.
**PITR:** Поняла важность непрерывной архивации WAL для восстановления на произвольный момент времени. Настроил параметры `wal_level`, `archive_mode` и `archive_command`. Научилась использовать `recovery_target` для точного управления процессом восстановления.
**Параллелизм:** Использование опции `-j` в `pg_dump` и `pg_restore` значительно ускоряет операции для больших БД. Формат directory необходим для параллельной работы.
**Обновление версий:** Логический метод обновления через дамп/восстановление — надёжный способ миграции между мажорными версиями PostgreSQL. Важно сохранять глобальные объекты отдельно через `pg_dumpall --globals-only`.
**Табличные пространства:** Научилась работать с табличными пространствами при создании копий и восстановлении. Использование `tablespace_map` позволяет изменить расположение данных при физическом восстановлении.
**Практические навыки:** Получила опыт работы с утилитами `pg_dump`, `pg_dumpall`, `pg_basebackup`, `pg_restore`. Поняла разницу между форматами дампов (plain, custom, directory, tar) и их применение в различных сценариях.
